# Repository Structure

This doc explains how the code is organized and the rules that keep six people (and AI agents) from colliding when working simultaneously.

**Skim this once at the start. Go to "The Short Version" at the bottom if you're in a rush.**

## Why we organized it this way

### One JSON file per program (the key decision)

**The problem:** All six program rules need to live *somewhere*. If they all live in one `rules.json` file, six people editing it simultaneously = merge conflicts all week.

**The solution:** Each program gets its own file in `data/programs/`. Two people can work on housing and childcare simultaneously without touching the same file.

**The build step:** `scripts/build_rules.py` merges all six files into `data/rules.json`, which the backend loads at startup. The merge script also validates:
- Every program has required fields
- Programs in the same `exclusivity_group` both declare it
- Every amount has a source document (文号)

**Rules for `rules.json`:**
- Never edit it by hand. Run the build script.
- If you get a merge conflict in it, don't fix the conflict. Delete the file and rerun the script.
- It's safe to commit or gitignore—either way is fine. Commit it if you're worried about the script breaking during the demo.

### Sources are human-written, never AI-generated

`data/manifest.json` records the 文号 (document number), official link, and agency name for each policy PDF. A human fills this in when uploading the document.

Why not let AI provide sources? A fake 文号 on a results card is the worst possible error—it looks like proof. The person who downloaded the PDF knows the real number. The AI only knows what it retrieved (and can hallucinate citations).

This matters for validation too: "every amount must trace back to a source document" is a meaningful check only if the sources are trustworthy.

### Raw extraction passes are kept as evidence

`data/extractions/` holds all three AI passes for each program (unedited, unfiltered). They're not used as inputs—`data/programs/*.json` is what the build script reads. But they're evidence:
- They show how the `confidence` score was computed
- They're what you show someone who asks "how do you know this rule is right?"
- They're what you diff if someone changes the extraction prompt—you can see if all the rules shifted

This is also why `docs/extraction-prompt.md` is in git and versioned. Changing the prompt invalidates every confidence score, so it lives where you can see its history.

### One matcher file per domain (parallel work)

Three domains → three matcher files (housing, childcare, employment). Each one is one person's responsibility.

All three matchers have the same interface:
```python
async def match(profile: Profile, rules: list[Rule]) -> list[MatchResult]
```

Because the interface is fixed (in `docs/api-contracts.md`), three people can work simultaneously without coordinating. Shared logic lives in `base.py`, owned by one person. This lets three teams run in parallel and merge cleanly.

### Frozen test profiles

`tests/fixtures/profiles.json` holds the three profiles you'll actually type into the demo. `test_golden.py` runs each one through the full system and asserts you get the same results every time. Run this before every merge—it catches breaks early and takes one second. It's the difference between a working demo and a broken one.

### Documentation at the root

`CONTEXT.md` and `ITERATE.md` live at the root because people read them top-to-bottom. Detailed reference docs (API shapes, schemas, prompts) live in `docs/` and get linked from `AGENTS.md`. This avoids duplicating large blocks of text in multiple places.

## AGENTS.md: The entry point

Keep this file around 50 lines. It's a map and command reference, not a full manual. Link `CLAUDE.md` to it so people on Cursor or Codex get the same file:

```bash
ln -s AGENTS.md CLAUDE.md
```

See the actual `AGENTS.md` for current content. It should include:
- What the system does (one sentence)
- Quick start commands (how to run it)
- The core rule (numbers from code, words from AI)
- Hard rules (don't break these)
- Where to find detailed docs (CONTEXT.md, ITERATE.md, docs/rule-schema.md, etc.)

The "what we're NOT building" section in CONTEXT.md matters for agents—point at it. Agents love adding databases and frameworks. That list is your answer.

## Ownership (write this first)

Create `docs/ownership.md` in the first hour. It's a simple table:

| Area | Owner | Files |
|------|-------|-------|
| Backend core | | `backend/main.py`, `models.py`, `rules.py`, `derive.py`, `matchers/base.py` |
| Housing matcher | | `backend/matchers/housing.py` |
| Childcare matcher | | `backend/matchers/childcare.py` |
| Employment matcher | | `backend/matchers/employment.py` |
| Benefit + sorting | | `backend/benefit.py`, `aggregator.py` |
| AI integration | | `scripts/extract.py`, `backend/explain.py`, `intake.py` |
| Frontend | | `frontend/` |
| Policy data | | `data/manifest.json`, `data/programs/`, `data/sources/` |

**Important:** `derive.py` is core, not domain-specific. It computes normalized fields that all three matchers use. If three people each write their own version, they'll disagree on what "第6档" means. So one person owns it.

**Branching strategy:**
- Short-lived branches named by area (feature/housing, feature/childcare)
- Merge back to main frequently (don't hold a branch open more than a day)
- If running multiple agents in parallel, give each one a git worktree so they don't fight over the same checkout:
  ```bash
  git worktree add ../subsidy-housing feature/housing
  ```
- Config in environment variables, not committed files (two worktrees editing the same config file = merge hell)

## Don't add these (even though they sound reasonable)

- **A database.** Six programs in memory. Postgres is overkill.
- **A build step for the frontend.** If npm and webpack show up, something went wrong.
- **An agent framework.** Parallelism is just `asyncio.gather()` over three functions.
- **A `utils/` folder.** It becomes a dumping ground and a merge-conflict magnet.
- **Skills in `.claude/` for everything.** Skills are for things you repeat. In one week you barely repeat anything. One skill for "how to add a program file correctly" might pay off, but not five.

(Agents love adding databases and frameworks. This list is your firewall.)

## Quick reference

1. **One file per program** in `data/programs/`. Build script merges them into `rules.json`.
2. **One matcher file per domain** (`housing.py`, `childcare.py`, `employment.py`). All have the same interface.
3. **Sources are human-written** in `data/manifest.json`. Never from AI.
4. **Extractions are kept** as evidence in `data/extractions/`.
5. **AGENTS.md is 50 lines**—commands, rules, and links to detailed docs.
6. **Ownership table first** — write `docs/ownership.md` before coding.
7. **Golden tests before merge** — run the demo profiles through the full system every time.
